# The interface — envelopes, exit codes, redaction, versioning

For anyone integrating this gateway. The engine's own integration rules
(exit codes `0/1/2`, strict mode, machine reports) are documented in the
engine repository and are **not** restated here; this document covers only
what the gateway adds.

---

## The rule, in one sentence

> **Read `exit_code` and `status`. A `status` of `completed` does not mean the
> artifact passed — it means the engine ran.**

---

## Operations

| Operation | Engine entry point | Required inputs |
|---|---|---|
| `verify` | `verify.py` | — (`inputs.corpus` optional) |
| `attestation` | `verify_attestation.py` | `inputs.attestation`, `inputs.trust_store` |

`attestation` **refuses** a request without a trust store. Without one the
engine cannot establish any identity and could only answer `NOT TESTED`; a
gateway that let the call through would return a report that looks like a
verification and is not one.

Operations the engine supports and this gateway does **not** expose yet:
binding (`bind.py`), signing (`sign.py`), timestamping (`timestamp.py`),
third-party package ingestion and reconciliation (`adapters/`). They are
future work, not omissions — adding one means adding an operation to the
request contract and a case to the suites.

## The request envelope

`neomundi.evidence.gateway.request/1` —
[`contracts/gateway-request-v1.json`](../contracts/gateway-request-v1.json).

```json
{
  "schema": "neomundi.evidence.gateway.request/1",
  "operation": "verify",
  "request_id": "whatever-the-caller-wants-to-correlate",
  "artifact": { "name": "evidence-v1-demo", "path": "examples/dossier-v1/NEOMUNDI_EVIDENCE_V1_DEMO.zip" },
  "inputs":   { "corpus": "examples/dossier-v1/corpus" },
  "options":  { "strict": true, "language": "fr" }
}
```

**`request_id` is never generated by the gateway.** An identifier it invented
would correlate with nothing the caller holds. Absent in, `null` out.

### The artifact root

Every path in a request is resolved under one directory — `--artifact-root`,
defaulting to the current directory. A path whose **resolved** form falls
outside it is refused with `path_outside_root`. The check is on the resolved
path, because a `..` segment or a symbolic link does not show up in the
string.

The example requests shipped in [`examples/`](../examples) use paths relative
to the **engine**, because that is where the engine's synthetic demonstration
dossier lives. Hence `--artifact-root "$EVIDENCE_ENGINE_HOME"` in the
quick-start. In a real integration, the artifact root is the directory where
the caller's submissions land, and it is normally **not** the engine.

## The response envelope

`neomundi.evidence.gateway.response/1` —
[`contracts/gateway-response-v1.json`](../contracts/gateway-response-v1.json).

| Field | What it is |
|---|---|
| `status` | `completed`, `rejected` or `engine_unavailable` |
| `verification_performed` | a fact about **this gateway run**, not about the artifact: true only when the engine ran and its report was read |
| `verdict` | `null` unless the engine ran. Every field copied from the engine report, with `source: "evidence-engine"` and `computed_by_gateway: false` |
| `artifact.sha256_reported_by_engine` | taken from the engine report. The gateway does **not** hash the artifact: doing so would be a second integrity implementation |
| `engine_report` | the engine's own report, verbatim except for path redaction. Its own `schema` field names the contract it follows |
| `engine.revision_declared` | declared by the operator through `EVIDENCE_ENGINE_REVISION`, and **never verified here** — `revision_is_declared_not_verified` is always `true` |
| `limits` | always non-empty: the gateway's two limits, plus every `does_not_establish` line of the engine report, prefixed `engine:` |
| `errors` | `reason`, `field`, `detail` — one entry on `rejected` and `engine_unavailable` |

## Exit codes

| Code | Meaning | Verification? |
|---|---|---|
| `0` | engine ran, no control failed | yes |
| `1` | engine ran, **at least one control failed** | yes |
| `2` | engine ran, strict mode, a **required** guarantee is not demonstrated | yes |
| `3` | **engine unavailable** | **no** |
| `4` | **request refused** | **no** |

`0`, `1` and `2` are the engine's, untranslated — `1` still wins over `2`
because that is the engine's rule and the gateway does not reinterpret it.

`3` and `4` exist for one reason: without them, "nothing failed" and "nothing
ran" would return the same code. A consumer that treats any non-zero code as
a refusal is not misled; a consumer that only checks `!= 0` for failure is
still correct.

### Refusal reasons (code 4)

`unsupported_request_schema` · `unknown_operation` · `unexpected_field` ·
`missing_field` · `field_type_invalid` · `request_not_an_object` ·
`request_unreadable` · `artifact_not_found` · `input_not_found` ·
`path_outside_root` · `unsupported_language`

### Unavailability reasons (code 3)

`engine_not_declared` · `engine_home_absent` · `engine_entrypoint_missing` ·
`engine_not_executable` · `engine_timeout` · `engine_report_absent` ·
`engine_report_unreadable`

The last two matter: a engine that ran but wrote no readable machine report
produces **no verdict here**. The gateway does not reconstruct one from the
text output. A verdict parsed out of prose would be a verdict the gateway
computed.

## Redaction — and why the report is not byte-identical

The engine writes the paths it was given into its report, including the
absolute path of the archive. On a workstation that path carries the account
name. An envelope sent to a caller has no business teaching them that.

So before republishing, the gateway rewrites, in **string values only**:

| What | Becomes |
|---|---|
| the engine root | `<engine>` |
| the artifact root | `<artifacts>` |
| the user's home directory | `<home>` |

Keys are never touched, and a digest cannot be: it contains no path
separator. The longest pattern is applied first, so an engine nested under
the home directory still reads `<engine>`.

This is stated, not silent: `engine_report_redacted` and
`redactions_applied` say that the republished report is **no longer
byte-identical** to what the engine wrote. Error details and the
human-readable summary line are redacted the same way.

If you need the engine's bytes exactly as written, run the engine directly —
that is what [`tests/test_no_verification_logic.py`](../tests/test_no_verification_logic.py)
does to prove the two agree.

## Versioning

The envelope identifiers end in `/1`. The policy is the engine's:

- a **new** field may appear in a response within `/1`;
- an existing field never changes meaning or type within `/1`;
- a breaking change gets `/2`, and `/1` keeps working or is withdrawn in the
  open — never moved silently;
- the request contract is **closed**. A field it does not allow is refused,
  not ignored, which is what makes adding one a visible event.

The gateway's own version (`gateway.version`, `0.1.0`) moves independently of
the envelope version.

## What a response does not establish

Beyond everything the engine itself does not establish:

- **independence.** The gateway and the engine run under the same operator
  unless that operator states otherwise. A report produced here is a
  verification performed by that operator — never an independent third-party
  verification, and never to be presented as one.
- **engine identity.** `revision_declared` is a declaration. This gateway
  runs no `git`, checks no signature over the engine tree, and cannot
  establish that a directory corresponds to a commit.
- **anything about the engine's own correctness.** That is what the engine's
  suites, its public conformance corpus and its second independent verifier
  are for.
